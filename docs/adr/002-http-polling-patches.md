# 002. Живые метрики через HTTP-поллинг патчей, не WebSocket

- Статус: принято
- Дата: 2026-09-16

## Контекст

Метрики на мок-сервере меняются каждые несколько секунд. Таблица должна подсвечивать изменившиеся ячейки без перезагрузки страницы.

Нужен канал «что изменилось после версии N». Кандидаты: WebSocket / SSE, длинный поллинг, короткий `GET` с `since`.

Стек доставки: Vite proxy в dev, nginx → Node в Docker. Нужен статус «онлайн / переподключение / нет сети» в шапке.

## Решение

Инкрементальный JSON-патч по HTTP:

```
GET /api/org-tree/changes?since={version}
```

Интервал ~5 с, backoff с джиттером. Тело — `OrganizationChanges` (см. [data-model.md](../data-model.md#контракт-патча-живой-ленты)). При `reset` — полный `GET /api/org-tree`. Снимок дополнительно рефетчится раз в 5 минут.

`ConnectionStatus` подписан на тот же Query-хук и отображает состояние поллинга как соединение.

## Альтернативы

- **WebSocket** — пуш без 5-секундной задержки, естественный «онлайн». Цена: протокол, реконнект, прокси (upgrade через nginx), отдельный lifecycle от Query. Для мока с интервалом 4 с выигрыш меньше сложности.
- **SSE** — односторонний пуш по HTTP, проще сокета. Всё ещё нужен реконнект и другой сервер, чем остальные `GET`.
- **Только полный рефетч дерева** — проще патча, но больше трафика и сложнее structural sharing: каждый тик — новый объект всего дерева.
- **TanStack Query + WebSocket как queryFn** — смешение push и pull, плохо ложится на `refetchInterval`.

## Последствия

- Контракт патча транспортно-нейтральный: тот же JSON можно отдать кадром WebSocket без смены `applyOrganizationChanges`.
- Задержка до UI ≈ интервал поллинга, не «сразу после мок-тика».
- nginx остаётся простым reverse proxy без `Upgrade`.
- Два Query: снимок и лента. Лента пишет в кэш снимка через `setQueryData` / `invalidateQueries`, а не держит вторую копию дерева.
- Пока нет сокета, документация описывает HTTP как факт и WS как целевой кадр, не как работающий канал.
