# 007. Поиск в таблице — детерминированный парсер, не LLM

- Статус: принято
- Дата: 2026-09-16

## Контекст

В шапке таблицы есть строка поиска. Требование — понимать фразы вроде «отделы с эффективностью ниже 70» и «бюджет больше 2 млн», с откатом к текстовому поиску по имени.

Внешний вызов модели в браузере тянет ключи, латентность, стоимость и раздувает бандл (лимит 200 КБ gzip).

## Решение

Клиентский парсер `src/Table/parseSearchQuery.ts`:

- регулярки для уровня (дивизион / отдел / команда / сквад), метрик, сравнений, чисел с «тыс» / «млн»
- успех → `StructuredFilter` (level, name, набор `MetricClause`)
- не разобрали → `TextFilter` по подстроке имени
- `applySearchFilter` режет уже посчитанные `OrganizationTableRow[]`
- debounce 250 мс, подсказка `describeSearchFilter`

Сервер о поиске не знает.

## Альтернативы

- **LLM на каждый ввод** — гибкий язык, непрогнозируемый фильтр, зависимость от сети, секреты, не укладывается в бюджет бандла, если тащить SDK.
- **SQL-подобная грамматика** (`level=2 AND kpi<70`) — точнее для сильных пользователей, хуже для заявленных русских фраз.
- **Фильтры-фасеты (селекты)** — нулевой парсер, беднее «AI-поиск» из README.

## Последствия

- Поведение воспроизводимо и покрывается тестами без мока модели.
- Неизвестные формулировки тихо деградируют в поиск по названию — это фича, не ошибка.
- Расширение языка = правка регулярок, не промпта.
- В продукте нет сетевого вызова LLM; слово «AI» в README относится только к разбору фразы.
